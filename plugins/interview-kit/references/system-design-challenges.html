Frame & size the problem

1 · Unclear requirements lead to the wrong architecture

“Fast” and “consistent” do not select a design until the relevant operation, workload, and measurable bar are stated.

TechniqueBenefit / whenCost / trade-off
Scope functions and exclusionsConcentrates design effort on the core operation.Exclusions must be explicit; designing adjacent features adds unjustified complexity.
Quantify latency and rank consistency per operationCreates discriminating criteria for reads versus correctness-sensitive writes.One system-wide ranking or arbitrary number can mislead the design.
Negotiate extreme product casesCan avoid engineering an exceptionally expensive tail.The guarantee no longer covers the excluded case.

Concept: requirements scoping · S1–S5

2 · Scale guesses cause premature distribution or peak overload

Average traffic and a large-sounding record count alone cannot justify infrastructure.

TechniqueBenefit / whenCost / trade-off
Estimate storage, peak operations and transfer timeTurns usage assumptions into bytes, requests per second, and feasibility checks.Answers depend on explicit behavioral assumptions; sizing on averages misses peaks.
Keep a single instance while estimates permitAvoids premature sharding and distributed coordination.Revisit when workload or capacity assumptions change; the library gives no universal threshold.

Concept: capacity estimation · S1, S2, S4, S5

Slow reads & difficult discovery

3 · High read latency: find the bottleneck before adding capacity

A point lookup, a hot object, a geographic round trip, and a multi-record aggregation have different remedies. Replicas and sharding are conditional, not substitutes for an index or a cache.

TechniqueBenefit / whenCost / trade-off
Index the point-lookup keyAvoids a table scan; a primary key also enforces uniqueness.Indexes consume storage and add work on writes; an index cannot remove network latency or multi-record fan-out.
Cache hot or mostly static reads in memoryReduces database reads and disk access; shortens the hot path.Cold misses hit origin; eviction, finite memory, stale data and invalidation add complexity.
Edge cache / CDN for distant readersMoves frequently read content nearer geographically distributed clients.Inconsistent invalidation between nodes, cost and low hit rates for rarely accessed data; personalized results may not be shareable.
Read replicas for staleness-tolerant queriesSpread read traffic while strongly consistent operations still go to the leader.Replica lag; capacity and placement require management. Do not send correctness-critical claims to stale replicas.
Partition by query localityRoutes scoped queries to a subset of data when one instance is under pressure.A poor key forces cross-partition fan-out; skew can overload one partition. Do not shard merely because the dataset sounds large.
Precompute expensive resultsReduces read-time assembly when it cannot meet the latency budget.Amplifies writes, increases stored state and can make results stale.

Concepts: point lookups, caching, read-heavy workloads, partitioning, fan-out · S1–S6

4 · Keyword search and complex filters scan or return stale data

Exact point indexes and wildcard text searches answer different query shapes.

TechniqueBenefit / whenCost / trade-off
Conventional indexes and query tuningEfficient for actual filter columns; bounded projections and limits reduce work.Weak for partial text matches; additional indexes slow writes and use space.
Database full-text indexWord search without a wildcard table scan in the existing database.Extra storage, query-specific maintenance and potentially slower queries than a standard index.
Dedicated inverted-index searchComplex and fuzzy text searches at higher traffic.Separate cluster and synchronization from the primary store; lag and failures cause stale or missing results.

Concept: full-text search · S3

5 · Personalized lists are slow, stale or run out

TechniqueBenefit / whenCost / trade-off
Indexed real-time candidate queriesReflects current filters and location without scanning every candidate.Search-index synchronization is difficult; delayed updates give stale results.
Precompute and cache listsFast initial access; background work can be scheduled off peak.Expensive to build for everyone; list exhaustion and changed preferences make results stale.
Cached first page plus early live refreshBalances initial speed with fresher continuation before exhaustion.Maintains two paths, freshness controls and a live fallback.
Persisted action history plus recent client filterExcludes older processed entries and masks replica lag for recent actions.Growing history makes filtering costlier; recent client filtering assumes one device.

Concepts: candidate generation, repeat exclusion · S6

6 · “Nearby” cannot be answered by straight-line distance alone

TechniqueBenefit / whenCost / trade-off
Geographic filtering before travel-time checksEliminates clearly distant candidates before expensive per-candidate evaluation.Requires a geographic bound that does not discard viable results.
Evaluate travel time on narrowed candidatesAnswers reachability more accurately than distance.Synchronous external calls add latency and have rate/capacity limits.
Cache slowly changing candidate locationsAvoids repeated location lookups on the read path.Cached candidate sets can age; fast-changing reachability still needs checking.

Concept: proximity filtering · S4

7 · Long ordered feeds and caller-specific availability cost too much to scan

TechniqueBenefit / whenCost / trade-off
Cursor aligned with an ordering indexContinues from the last boundary without restarting at the first page.Unindexed sort or cursor causes scans; bounded precomputed lists need an exhaustion fallback.
Filter reachable locations, then aggregate instancesAvoids a meaningless global total and a scan of all locations.Extra caller-specific read work; a displayed total is not a guaranteed claim.

Concepts: cursor pagination, availability aggregation · S4, S5

Skew, spikes & availability

8 · Read volume overwhelms one service or database

TechniqueBenefit / whenCost / trade-off
Stateless service replicasDistribute requests and provide redundant frontends.Shared state cannot remain in process; increasing app instances does not fix a saturated datastore.
Separate read and write pathsScale asymmetric workloads independently.Adds service boundaries and operational structure; not justified merely by a small read/write difference.
Replicate stateful dependenciesRedirect traffic after a server failure.Replica coordination and failover cost; backups recover data but do not replace live serving.

Concepts: read-heavy workloads, redundancy · S1, S2, S3, S4, S5

9 · A few hot keys saturate one shard despite ample aggregate capacity

TechniqueBenefit / whenCost / trade-off
Sharded cache using the same keyHelps when load is evenly distributed.Does not solve a hot key; moves the skew to a cache shard.
Replicated per-instance caches for hot readsEach instance serves its own hot copy without coordinating every read.Duplicates memory and causes one initial miss per instance; edited entries need invalidation.

Concept: hot-key load distribution · S5

10 · A read fans out widely, or a write must reach too many readers

TechniqueBenefit / whenCost / trade-off
Assemble on readCheap writes; avoids precomputing for enormous fan-out.Read-time gather and merge can breach latency targets.
Fan out on write through a queue and worker fleetFast reads from precomputed data; moves the heavy write off the request path.Write amplification, asynchronous staleness, uneven queue-job costs and worker throughput needs.
Hybrid per-entity policy and bounded precomputeUse write fan-out for manageable cases, read merge for extreme ones; cap precomputed depth.Multiple paths to maintain; deep consumers need a read fallback.

Concept: fan-out on read vs write · S5

11 · Demand for scarce inventory exceeds supply

TechniqueBenefit / whenCost / trade-off
Push availability more frequentlyCan make moderate shared-view changes visible promptly.At extreme contention, views churn faster than people can act; it cannot increase supply.
Server-enforced admission queueLimits simultaneous contenders and repeated failed selections.Users wait; connection drops, estimated waits and queue throughput are additional concerns.

Concept: admission control · S3

Concurrency, identity & data modeling

12 · Two claimants can allocate the same finite resource

TechniqueBenefit / whenCost / trade-off
Database transaction and conditional claimStore-level guarantee prevents double allocation; colocated data keeps atomicity local.Row contention; holding locks through human-facing payment steps is too long.
Expiring hold with read-time expiry predicateReleases abandoned holds without making a cleanup job correctness-critical.Expiry can occur during a slow payment; final claim must be rechecked.
External expiring lock / claim storeAtomic acquisition and automatic expiry without long database locks.Two stores introduce failure and reconciliation paths; database constraint still provides the final guarantee.
Sequential acquisition with rollback for multi-item claimsCan release partial acquisitions when an all-or-nothing set is required.Partial failures, overlapping claims and rollback add complexity.

Concepts: double allocation, record expiry · S1, S3, S4

13 · Simultaneous reciprocal actions miss the immediate result

TechniqueBenefit / whenCost / trade-off
Periodic reconciliationEventually finds missed pairs.Delays feedback and repeatedly loads the database.
Pair-derived key and single-partition conditional operationPlaces both directions together for an atomic decision.Conditional transactions add node round trips; partition growth and hot pairs need management.
Atomic in-memory script and durable historyLow-latency reciprocal detection in one operation.Node failures, rebalancing and memory pressure; the source does not establish exactly-once delivery.

Concept: atomic reciprocal actions · S6

14 · Unique identifiers collide or require cross-instance coordination

TechniqueBenefit / whenCost / trade-off
Truncated hash or random code with collision detectionCompact, nonsequential identifiers; deterministic hash supports deduplication.Collision probability grows with volume; checking/retrying costs writes, and determinism may not fit multiple IDs per input.
Shared atomic increment then encodeUnique values across stateless writers.Shared counter and round trip; sequential codes are predictable.
Allocate ranges in batches or by regionReduces counter calls and cross-region coordination.Unused ranges leave gaps; failover and range ownership need attention.

Concepts: identifier generation, counter coordination · S1, S2

15 · Expired or changed data remains visible in a cache

TechniqueBenefit / whenCost / trade-off
Enforce expiry on reads; cache TTL no longer than record lifetimeCorrect visible state even if deletion is delayed; cache can evict automatically.Expired rows may remain in storage until cleaned.
Cleanup jobReclaims storage.A late or failed sweep cannot be the only correctness mechanism.
Short TTL or invalidate on changeBounds stale reads after edits and personalized-list changes.More origin requests, invalidation coordination and miss load.

Concepts: expiry, read caching · S1, S3, S4, S5, S6

16 · A reverse relationship query cannot use a one-sided embedded list

TechniqueBenefit / whenCost / trade-off
Duplicate inverse relationshipFast lookups in both directions.Two copies can diverge and must be synchronized.
Link entity / join table with query-side key or indexSupports reverse lookups and attributes on each link without scanning all owners.Additional lookup versus reading an embedded list; indexes also cost writes.
Graph store for multi-hop traversalsFits graph-style navigation.Operational scaling cost without benefit for one- or two-hop access.

Concepts: relationship queries, entity granularity · S2–S5

17 · Wrong entity or service boundaries make reads expensive and writes fragile

TechniqueBenefit / whenCost / trade-off
Separate reusable type from physical instanceModels shared description once while tracking per-instance state.Requires joins or a derived view for caller-facing aggregates.
Keep coupled state in one ACID storeSupports atomic claims and avoids distributed recovery when operations cross entities.May constrain independent scaling when query or write patterns diverge.
Split divergent read/search or high-volume write workloadsEach path can scale to its own query shape and write rate.Cross-store synchronization and new operational boundaries.

Concepts: entity granularity, service/data boundaries · S3–S6

Transfers, client state & external systems

18 · Large uploads time out or restart from zero

TechniqueBenefit / whenCost / trade-off
Client-side chunking and parallel transferResumes missing pieces, exposes progress and uses available bandwidth.Tracks per-piece state; server-side chunking alone still requires the full original request.
Storage-provider multipart uploadDelegates part assembly to the object store.Completion fires after assembly, not after each part; progress needs part inspection.
Whole-file and per-chunk fingerprintsIdentify duplicate content and already-transferred pieces.Hashes are not user record identities; names are not unique, and client-reported state needs verification.

Concepts: large transfers, content identity · S2

19 · Application servers relay every payload byte unnecessarily

TechniqueBenefit / whenCost / trade-off
Keep small payloads on a serverSimple at small scale.Disk and machine failure limit durability and growth.
Relay through the application to storageDecouples bulk storage from application disk.Transfers each byte twice through the server.
Direct-to-storage signed transfer; optional CDNSeparates authorization/metadata control from the bulk data path; edge delivery helps distant frequent readers.Transfer and metadata can disagree; signed links grant access until expiry, and edge caching costs money.

Concepts: bypassing the server, signed URLs · S2

20 · Network transfer is costly, but compression is not always worthwhile

TechniqueBenefit / whenCost / trade-off
Compress text before transfer and encryptionCan significantly reduce bytes; Brotli favors text ratio, Zstandard favors speed, Gzip offers broad support.Compression and decompression cost CPU; algorithm support and network conditions matter.
Skip recompressing already compressed mediaAvoids CPU for little bandwidth gain.Transfers close to original size.

Concept: compression trade-offs · S2

21 · Client copies drift after server-side changes

TechniqueBenefit / whenCost / trade-off
Poll for updates since last syncSimple and recovers missed changes.Delayed detection and empty-request bandwidth.
Push over one persistent connection per deviceNear-real-time notices; one-way SSE suffices if the server alone sends.Connections drop, notifications can be missed and connection management is harder.
Push with periodic polling fallbackFast common path plus eventual recovery.Runs two mechanisms and must query changes by watched records and update time.

Concept: propagating changes · S2, S3

22 · Client or provider reports a successful operation that the server cannot verify

TechniqueBenefit / whenCost / trade-off
Trust a client completion flagFast and simple when the server never saw the direct transfer.May mark missing data complete; client state can disagree with storage.
Verify against storage or provider stateChecks whether client-reported progress/completion really happened.Extra reads, delayed completion and a reconciliation path.
Idempotent callback and atomic internal updateProvider retries do not duplicate state changes; related internal state changes commit together.Must track operation identity and handle successful external work with failed internal updates.

Concepts: client verification, external operations · S2–S4

23 · Client-side caching prevents later updates or revocation

TechniqueBenefit / whenCost / trade-off
Cacheable permanent responseFewer future server requests for a stable mapping.Client may stay pinned after a change; server loses per-request visibility and cannot recall cached responses.
Nonpermanent responseKeeps the mapping under server control and preserves request statistics.More requests reach the server; less client caching benefit.

Concept: client-cached responses · S1
