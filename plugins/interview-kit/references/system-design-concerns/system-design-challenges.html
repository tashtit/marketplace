Frame & size the problem

1 · Unclear requirements lead to the wrong architecture

“Fast” and “consistent” do not select a design until the relevant operation, workload, and measurable bar are stated.

TechniqueBenefit / whenCost / trade-offExample from source
Scope functions and exclusionsConcentrates design effort on the core operation.Exclusions must be explicit; designing adjacent features adds unjustified complexity.Exclude analytics and account management from the short-link core. [S1]
Quantify latency and rank consistency per operationCreates discriminating criteria for reads versus correctness-sensitive writes.One system-wide ranking or arbitrary number can mislead the design.Require search under 500ms, but strong consistency only for item claims. [S3]
Negotiate extreme product casesCan avoid engineering an exceptionally expensive tail.The guarantee no longer covers the excluded case.Discuss a maximum file size before designing the upload path. [S2]

2 · Scale guesses cause premature distribution or peak overload

Average traffic and a large-sounding record count alone cannot justify infrastructure.

TechniqueBenefit / whenCost / trade-offExample from source
Estimate storage, peak operations and transfer timeTurns usage assumptions into bytes, requests per second, and feasibility checks.Answers depend on explicit behavioral assumptions; sizing on averages misses peaks.1B links × 500 bytes ≈ 500GB of storage. [S1]
Keep a single instance while estimates permitAvoids premature sharding and distributed coordination.Revisit when workload or capacity assumptions change; the library gives no universal threshold.The short-link estimate fits a reasonable database without starting with sharding. [S1]

Slow reads & difficult discovery

3 · High read latency: find the bottleneck before adding capacity

A point lookup, a hot object, a geographic round trip, and a multi-record aggregation have different remedies. Replicas and sharding are conditional, not substitutes for an index or a cache.

TechniqueBenefit / whenCost / trade-offExample from source
Index the point-lookup keyAvoids a table scan; a primary key also enforces uniqueness.Indexes consume storage and add work on writes; an index cannot remove network latency or multi-record fan-out.Index the short code to resolve a redirect without scanning 1B links. [S1]
Cache hot or mostly static reads in memoryReduces database reads and disk access; shortens the hot path.Cold misses hit origin; eviction, finite memory, stale data and invalidation add complexity.Cache frequently accessed, rarely edited short-link destinations in memory. [S1]
Edge cache / CDN for distant readersMoves frequently read content nearer geographically distributed clients.Inconsistent invalidation between nodes, cost and low hit rates for rarely accessed data; personalized results may not be shareable.Serve popular short links from geographically distributed edge locations. [S1]
Read replicas for staleness-tolerant queriesSpread read traffic while strongly consistent operations still go to the leader.Replica lag; capacity and placement require management. Do not send correctness-critical claims to stale replicas.Send slightly stale local-inventory reads to replicas, but order transactions to the leader. [S4]
Partition by query localityRoutes scoped queries to a subset of data when one instance is under pressure.A poor key forces cross-partition fan-out; skew can overload one partition. Do not shard merely because the dataset sounds large.Partition nearby inventory by the first three zipcode digits; most queries touch one or two partitions. [S4]
Precompute expensive resultsReduces read-time assembly when it cannot meet the latency budget.Amplifies writes, increases stored state and can make results stale.Precompute a bounded feed of about 200 item IDs, then fall back to live queries when exhausted. [S5]

4 · Keyword search and complex filters scan or return stale data

Exact point indexes and wildcard text searches answer different query shapes.

TechniqueBenefit / whenCost / trade-offExample from source
Conventional indexes and query tuningEfficient for actual filter columns; bounded projections and limits reduce work.Weak for partial text matches; additional indexes slow writes and use space.Index item name, date, performer, and location; limit results and inspect plans. [S3]
Database full-text indexWord search without a wildcard table scan in the existing database.Extra storage, query-specific maintenance and potentially slower queries than a standard index.Search specific words in item names with the database’s own full-text index. [S3]
Dedicated inverted-index searchComplex and fuzzy text searches at higher traffic.Separate cluster and synchronization from the primary store; lag and failures cause stale or missing results.Use an inverted index for typo-tolerant search, synchronized via change data capture. [S3]

5 · Personalized lists are slow, stale or run out

TechniqueBenefit / whenCost / trade-offExample from source
Indexed real-time candidate queriesReflects current filters and location without scanning every candidate.Search-index synchronization is difficult; delayed updates give stale results.Filter nearby profiles using a geospatial index and current preferences. [S6]
Precompute and cache listsFast initial access; background work can be scheduled off peak.Expensive to build for everyone; list exhaustion and changed preferences make results stale.Prewarm candidate lists for recently active users rather than recomputing everyone’s list. [S6]
Cached first page plus early live refreshBalances initial speed with fresher continuation before exhaustion.Maintains two paths, freshness controls and a live fallback.Show cached candidates first; query fresh candidates before the list runs out. [S6]
Persisted action history plus recent client filterExcludes older processed entries and masks replica lag for recent actions.Growing history makes filtering costlier; recent client filtering assumes one device.Keep the last K actions on the device while the backend excludes older persisted actions. [S6]

6 · “Nearby” cannot be answered by straight-line distance alone

TechniqueBenefit / whenCost / trade-offExample from source
Geographic filtering before travel-time checksEliminates clearly distant candidates before expensive per-candidate evaluation.Requires a geographic bound that does not discard viable results.Discard locations outside a 60-mile radius before drive-time checks. [S4]
Evaluate travel time on narrowed candidatesAnswers reachability more accurately than distance.Synchronous external calls add latency and have rate/capacity limits.Ask the routing provider for drive time only for surviving nearby locations. [S4]
Cache slowly changing candidate locationsAvoids repeated location lookups on the read path.Cached candidate sets can age; fast-changing reachability still needs checking.Synchronize slow-changing location coordinates into memory every five minutes. [S4]

7 · Long ordered feeds and caller-specific availability cost too much to scan

TechniqueBenefit / whenCost / trade-offExample from source
Cursor aligned with an ordering indexContinues from the last boundary without restarting at the first page.Unindexed sort or cursor causes scans; bounded precomputed lists need an exhaustion fallback.Use the oldest feed timestamp as the next-page boundary in an ordered index. [S5]
Filter reachable locations, then aggregate instancesAvoids a meaningless global total and a scan of all locations.Extra caller-specific read work; a displayed total is not a guaranteed claim.Find reachable locations first, then sum available physical instances of the requested type. [S4]

Skew, spikes & availability

8 · Read volume overwhelms one service or database

TechniqueBenefit / whenCost / trade-offExample from source
Stateless service replicasDistribute requests and provide redundant frontends.Shared state cannot remain in process; increasing app instances does not fix a saturated datastore.Load-balance short-link reads across multiple stateless application instances. [S1]
Separate read and write pathsScale asymmetric workloads independently.Adds service boundaries and operational structure; not justified merely by a small read/write difference.Separate the read-heavy feed path from its very different write-query path. [S5]
Replicate stateful dependenciesRedirect traffic after a server failure.Replica coordination and failover cost; backups recover data but do not replace live serving.Replicate the short-link database so traffic can shift when a server fails. [S1]

9 · A few hot keys saturate one shard despite ample aggregate capacity

TechniqueBenefit / whenCost / trade-offExample from source
Sharded cache using the same keyHelps when load is evenly distributed.Does not solve a hot key; moves the skew to a cache shard.Cache recent popular feed records by ID with a long TTL and LRU eviction. [S5]
Replicated per-instance caches for hot readsEach instance serves its own hot copy without coordinating every read.Duplicates memory and causes one initial miss per instance; edited entries need invalidation.Let every cache instance serve a trending record; the load balancer spreads its reads. [S5]

10 · A read fans out widely, or a write must reach too many readers

TechniqueBenefit / whenCost / trade-offExample from source
Assemble on readCheap writes; avoids precomputing for enormous fan-out.Read-time gather and merge can breach latency targets.Gather followed entities’ records and merge/sort them at request time. [S5]
Fan out on write through a queue and worker fleetFast reads from precomputed data; moves the heavy write off the request path.Write amplification, asynchronous staleness, uneven queue-job costs and worker throughput needs.Queue creator and record IDs; workers populate followers’ precomputed feeds. [S5]
Hybrid per-entity policy and bounded precomputeUse write fan-out for manageable cases, read merge for extreme ones; cap precomputed depth.Multiple paths to maintain; deep consumers need a read fallback.Skip write fan-out for extreme creators; merge their live results with a ~200-ID feed. [S5]

TechniqueBenefit / whenCost / trade-offExample from source
Push availability more frequentlyCan make moderate shared-view changes visible promptly.At extreme contention, views churn faster than people can act; it cannot increase supply.Push shared inventory-view changes to clients via server-sent events. [S3]
Server-enforced admission queueLimits simultaneous contenders and repeated failed selections.Users wait; connection drops, estimated waits and queue throughput are additional concerns.Queue entrants for a popular event; verify admission in a TTL-backed set before claims. [S3]

Concurrency, identity & data modeling

12 · Two claimants can allocate the same finite resource

TechniqueBenefit / whenCost / trade-offExample from source
Database transaction and conditional claimStore-level guarantee prevents double allocation; colocated data keeps atomicity local.Row contention; holding locks through human-facing payment steps is too long.Use a short transaction with isolation and conditional update to reserve one item. [S3]
Expiring hold with read-time expiry predicateReleases abandoned holds without making a cleanup job correctness-critical.Expiry can occur during a slow payment; final claim must be rechecked.Treat a reserved item whose hold timestamp has passed as available on the next read. [S3]
External expiring lock / claim storeAtomic acquisition and automatic expiry without long database locks.Two stores introduce failure and reconciliation paths; database constraint still provides the final guarantee.Acquire a TTL-backed external claim atomically, then keep the database as final guard. [S3]
Sequential acquisition with rollback for multi-item claimsCan release partial acquisitions when an all-or-nothing set is required.Partial failures, overlapping claims and rollback add complexity.Reserve several requested seats in order; release acquired seats if a later claim fails. [S3]

13 · Simultaneous reciprocal actions miss the immediate result

TechniqueBenefit / whenCost / trade-offExample from source
Periodic reconciliationEventually finds missed pairs.Delays feedback and repeatedly loads the database.Periodically scan for two users who both acted on each other after a race. [S6]
Pair-derived key and single-partition conditional operationPlaces both directions together for an atomic decision.Conditional transactions add node round trips; partition growth and hot pairs need management.Sort the two user IDs into one pair key and use a single-partition conditional action. [S6]
Atomic in-memory script and durable historyLow-latency reciprocal detection in one operation.Node failures, rebalancing and memory pressure; the source does not establish exactly-once delivery.Use one Redis Lua operation to record a swipe and check the reciprocal swipe. [S6]

14 · Unique identifiers collide or require cross-instance coordination

TechniqueBenefit / whenCost / trade-offExample from source
Truncated hash or random code with collision detectionCompact, nonsequential identifiers; deterministic hash supports deduplication.Collision probability grows with volume; checking/retrying costs writes, and determinism may not fit multiple IDs per input.Hash and encode a URL into a short code, checking for collisions before insertion. [S1]
Shared atomic increment then encodeUnique values across stateless writers.Shared counter and round trip; sequential codes are predictable.Atomically increment a shared counter, then Base62-encode each new short-link ID. [S1]
Allocate ranges in batches or by regionReduces counter calls and cross-region coordination.Unused ranges leave gaps; failover and range ownership need attention.Lease 1,000 counter values per instance or assign disjoint ID ranges to regions. [S1]

15 · Expired or changed data remains visible in a cache

TechniqueBenefit / whenCost / trade-offExample from source
Enforce expiry on reads; cache TTL no longer than record lifetimeCorrect visible state even if deletion is delayed; cache can evict automatically.Expired rows may remain in storage until cleaned.Filter expired short links during lookup; do not cache beyond their expiration. [S1]
Cleanup jobReclaims storage.A late or failed sweep cannot be the only correctness mechanism.Sweep expired short-link records to reclaim space after reads already reject them. [S1]
Short TTL or invalidate on changeBounds stale reads after edits and personalized-list changes.More origin requests, invalidation coordination and miss load.Invalidate rarely edited feed records when they change. [S5]

16 · A reverse relationship query cannot use a one-sided embedded list

TechniqueBenefit / whenCost / trade-offExample from source
Duplicate inverse relationshipFast lookups in both directions.Two copies can diverge and must be synchronized.Maintain a user-to-shared-record inverse mapping alongside the embedded share list. [S2]
Link entity / join table with query-side key or indexSupports reverse lookups and attributes on each link without scanning all owners.Additional lookup versus reading an embedded list; indexes also cost writes.Store (record ID, recipient ID) links so recipients can find records shared with them. Graph store for multi-hop traversalsFits graph-style navigation.Operational scaling cost without benefit for one- or two-hop access.Use a graph store for friends-of-friends navigation, not just a simple follow lookup. [S5]

17 · Wrong entity or service boundaries make reads expensive and writes fragile

TechniqueBenefit / whenCost / trade-offExample from source
Separate reusable type from physical instanceModels shared description once while tracking per-instance state.Requires joins or a derived view for caller-facing aggregates.Separate an item type from each physical item held at a particular location. [S4]
Keep coupled state in one ACID storeSupports atomic claims and avoids distributed recovery when operations cross entities.May constrain independent scaling when query or write patterns diverge.Keep inventory and claims together so the claim transaction is atomic. [S4]
Split divergent read/search or high-volume write workloadsEach path can scale to its own query shape and write rate.Cross-store synchronization and new operational boundaries.Separate a catalog search index from transactional inventory, or frequent action writes from profiles. [S4][S6]

Transfers, client state & external systems

18 · Large uploads time out or restart from zero

TechniqueBenefit / whenCost / trade-offExample from source
Client-side chunking and parallel transferResumes missing pieces, exposes progress and uses available bandwidth.Tracks per-piece state; server-side chunking alone still requires the full original request.Split a large upload into client-side 5–10MB pieces and resume only missing pieces. [S2]
Storage-provider multipart uploadDelegates part assembly to the object store.Completion fires after assembly, not after each part; progress needs part inspection.Initiate multipart upload, send parts, and mark complete after object-store assembly. [S2]
Whole-file and per-chunk fingerprintsIdentify duplicate content and already-transferred pieces.Hashes are not user record identities; names are not unique, and client-reported state needs verification.Fingerprint a whole file for deduplication and each chunk for resumable transfer. [S2]

19 · Application servers relay every payload byte unnecessarily

TechniqueBenefit / whenCost / trade-offExample from source
Keep small payloads on a serverSimple at small scale.Disk and machine failure limit durability and growth.Store files on an application server’s disk for a small-scale first design. [S2]
Relay through the application to storageDecouples bulk storage from application disk.Transfers each byte twice through the server.Store bytes in object storage while the application proxies the upload. [S2]
Direct-to-storage signed transfer; optional CDNSeparates authorization/metadata control from the bulk data path; edge delivery helps distant frequent readers.Transfer and metadata can disagree; signed links grant access until expiry, and edge caching costs money.Issue a signed upload URL; the client sends bytes to storage, not the API server. [S2]

20 · Network transfer is costly, but compression is not always worthwhile

TechniqueBenefit / whenCost / trade-offExample from source
Compress text before transfer and encryptionCan significantly reduce bytes; Brotli favors text ratio, Zstandard favors speed, Gzip offers broad support.Compression and decompression cost CPU; algorithm support and network conditions matter.Compress a 5GB text payload to around 1GB before upload. 21 · Client copies drift after server-side changes

TechniqueBenefit / whenCost / trade-offExample from source
Poll for updates since last syncSimple and recovers missed changes.Delayed detection and empty-request bandwidth.Ask for watched records updated since the client’s last-sync timestamp. [S2]
Push over one persistent connection per deviceNear-real-time notices; one-way SSE suffices if the server alone sends.Connections drop, notifications can be missed and connection management is harder.Keep one persistent notification connection per device, not one per file. [S2]
Push with periodic polling fallbackFast common path plus eventual recovery.Runs two mechanisms and must query changes by watched records and update time.Push remote-file changes immediately; poll every few minutes for missed events. [S2]

22 · Client or provider reports a successful operation that the server cannot verify

TechniqueBenefit / whenCost / trade-offExample from source

Verify against storage or provider stateChecks whether client-reported progress/completion really happened.Extra reads, delayed completion and a reconciliation path.Check the object store’s part listing rather than trusting client-reported progress. [S2]

23 · Client-side caching prevents later updates or revocation

TechniqueBenefit / whenCost / trade-offExample from source
Cacheable permanent responseFewer future server requests for a stable mapping.Client may stay pinned after a change; server loses per-request visibility and cannot recall cached responses.A permanent short-link redirect can be cached by a browser and bypass later lookups. [S1]
Nonpermanent responseKeeps the mapping under server control and preserves request statistics.More requests reach the server; less client caching benefit.Use a temporary redirect so changing a short link still takes effect on the next request. [S1]
